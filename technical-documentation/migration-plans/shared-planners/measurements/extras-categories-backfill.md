# What the extras categories backfill found

Raw figures taken from the local dev database and from the restored copy of live
(`eve_industry_planner_snapshot`) on 2026-09-15, after `prepareRelease` was run on dev with
`backfillPlannerExtrasCategories` in the build.

## Dev, after the run

| Figure | Count |
|---|---|
| Accounts holding extras categories | 13 |
| Of those, with no planner settings document | 0 |
| Of those, with a category their planner does not hold | 0 |
| `planner_settings` documents | 16 |
| Documents the step changed | 0 |

The step moved nothing, and the `planner_settings_pre_0_9_0` copy holds the same category ids as the
live collection for all 16 documents. Dev's planners were already current, so **this run is not
evidence that the merge does its job** — the divergent case is covered by
`TestLive_backfillPlannerExtrasCategories_movesWhatTheAccountAddedLater` and by nothing else.

## Live, before the release

| Figure | Count |
|---|---|
| Accounts with a settings document | 4822 |
| Of those, carrying a category of their own | 4 |
| Categories of their own, in total | 4 |

The snapshot carries no `planner_settings` collection: live has not run this release, so every planner
is seeded from its account's current list when it does. **The step is therefore a no-op on a first
live run**, by design — it exists for a database where planner settings were written earlier and the
account went on editing its own list afterwards, which is what dev and any environment already running
Stage C are.

Four accounts is the whole blast radius of getting the categories wrong, and each of those four would
lose a category they created rather than one of the six defaults.

## What the revert then showed

`revertRelease` was run on dev on 2026-09-15, after the run above. It restored the ten collections
recorded on 09-10 — the owner stamps are gone from `archived_jobs`, `job_groups` and the statistics
collections — and left the planner documents standing, because two of the three collections the planner
steps write had never been copied.

| Collection | After the revert | Why |
|---|---|---|
| `planners` | 13 documents, all owned | Never copied, so there was nothing to put back |
| `planner_memberships` | 17 documents, all owned | The same |
| `planner_settings` | 16 documents, all owned | Copied, but on 09-15 — so restored to that, not dropped |
| `accounts` | 12 documents | Restored to the 09-10 copy |

The mismatch between 12 accounts and 13 planners is the shape of the problem: one planner, four
settings documents and one membership row now name an account the revert rolled away. Nothing reads
them, and a re-run of `prepareRelease` is insert-only and would step over them, but dev is no longer at
a state live has ever been in.

**The fix is in the release rather than in the data**: `accountPlannerCollections` now carries all
three, so a first run copies them while they are empty, records zero, and a revert drops them — which
is the pre-release state. `TestTheBackupCoversWhatThePlannerStepsCreate` names the three explicitly, so
a fourth collection written by `EnsurePlanner` has to be added here too.

The statistics rebuild queue is deliberately **not** copied. Its two steps drop entries that name no
owner and then queue every account again, so its contents are regenerated by the run rather than
carried across it.

## The account the step kept reporting was a test leftover

Every run reported `1 account(s) have no planner settings`. It was
`eip-parity-planner-account-settings`, written by the live Mongo parity tests and never removed,
because those tests deleted their scratch data on the test's own context — and `defer cancel()` runs
before `t.Cleanup`, so the deletes ran against a cancelled context and failed silently into `_`. Most
tests in that file already built a fresh context for cleanup; the one that seeds settings from an
account did not, and neither did the three added with this step. All four now do, and the leftover
document has been removed from dev.

## The `planner_settings` backup is not a pre-release copy on dev

The other ten collections were copied on 2026-09-10; `planner_settings` was copied on 2026-09-15,
because it only joined `releaseTouchedCollections()` with the step that writes it and
`backupCollections` never replaces a copy it has already recorded. By the time it was taken, the
09-10 run had already created those documents.

So on dev, reverting 0.9.0 would restore `planner_settings` to its 2026-09-15 state rather than to
its pre-release state, which was no collection at all. A record of zero documents is what would have
dropped it, which is what the 09-10 run would have written had the collection been in the list then.
It costs nothing on dev, where the step changed nothing; it is worth correcting before the same
sequence is run anywhere it matters.
