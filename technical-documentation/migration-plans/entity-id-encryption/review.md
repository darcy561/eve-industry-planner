# Entity id encryption — review

**Rules:** Read and following [`../documentation-rules.md`](../documentation-rules.md)
and [`../technical-rules.md`](../technical-rules.md) (migration-plans).
This review edits nothing outside the project folder and does not move any status in `plan.md`;
it records what the code bears out so the plan can be corrected deliberately.

Verified against the working tree on 2026-10-05 (HEAD 051f79cf9 plus uncommitted changes).

## Summary

The project names EVE characters, corporations and alliances internally by ref, and encrypts ESI
refresh tokens at rest. The primitive, the boundaries and the token encryption are in the code as
the plan says. What the plan calls "one operator sweep and two pieces of cleanup" is larger than it
reads, for one reason the plan does not know about: the job reshape that ships in the same release
moved the linked-job rows from `build.costs.linkedJobs[]` to `esi.industryJobs`, keyed by `job_id`.
The sweep's `RawIDFilter()` still names the old path, so the verify gate the plan specifies would
count zero on a reshaped database whether or not anything was converted, and a sweep run before the
reshape reads a document through a model that no longer describes its rows.

Two things need attention first: how the conversion runs inside the release window (the core
service holds no `ENTITY_ID_KEY`, so a step cannot convert in-process as the stack stands), and the
live count of plaintext refresh-token rows, which gates the whole of the fallback cleanup and has
not been taken.

### Discrepancies

1. **One job read handler does not restore ids.** [overlay.md](./overlay.md) § Response says
   `jobidentity.Decrypt` runs "in every job read handler". It runs in
   `jobdocuments/getHandlers.go` (`decryptJob`, `decryptJobs`) and in `archivedjobs/restore.go`.
   `GetArchivedJobHandler` in `services/api/v1endpoints/archivedjobs/getJob.go` loads a
   `models.Job` and encodes it with no decrypt, so a linked job's `corporation_id` is absent from
   `GET /api/v1/archived-jobs/{jobID}`: the id field is zero and `omitzero`, the ref is `json:"-"`.
   Nothing is lost in storage, because an archived job is not echoed back through a write.
2. **Redis still holds raw ids, and nothing reads them.** The overlay records this. The detail it
   does not have: `RefreshTokenData.Corporations` and `.Alliances`
   (`services/shared/plannersession/types.go`) are assigned in `authenticate.go` and `refresh.go`
   and read by no non-test code, so the `custom_claims_corporations:` and
   `custom_claims_alliances:` caches (`plannersession/keys.go`, 30-day `CorporationTTL`) feed a
   write-only field. They are removable today without waiting on another project.
3. **`protectedfields.ValuesForIDs` and `ValuesForIDs64` are still present** with no caller but
   `TestRefsForIDsMatchesConversion`. The overlay says they go with the grants fill; they have not.
4. **A ref can reach a browser on a delivery from an organisation-owned planner.**
   [shared-planners/plan.md](../shared-planners/plan.md) § Stage G, G5 records it and does not act:
   `core/changestream/watcher.go` copies the stored document whole, and
   `outgoinglogic.restoreEntityIDs` rewrites only keys ending `_ref` or `Ref`, so
   `document._meta.owner.id` and a `document._id` that is itself an owner key pass through. No
   such document exists until corporation and alliance planners land, so this is latent.
5. **The enumeration defect is narrower than stated.** `runEncodeJobIdentity` distincts on the
   literal `"_meta.accountID"` while the worker filters through `eipmongo.OwnerFilter`. But
   `stampMetaOwner` (`release_meta_owner.go`) deliberately leaves `_meta.accountID` behind, and
   `reshapeJobDocument` keeps `_meta` whole (`reshapedJobFields`), so every document old enough to
   need conversion still carries the field. Read from code, the command enumerates those accounts
   today and stops doing so the day an operator removes the field. "Prints `0 accounts`" was not
   reproduced here and should be measured before it is repeated. The fix is the same either way.
6. **`RawIDFilter()` names a path the release removes.** It matches
   `build.costs.linkedJobs.corporation_id`. `reshapeJobDocument` moves those rows to
   `esi.industryJobs` keyed by `job_id` and deletes `build.costs`; `models.JobESI.LinkedJobs` is
   `map[string]LinkedESIJob` at `bson:"industryJobs"`. On a reshaped document the raw id sits at
   `esi.industryJobs.<job_id>.corporation_id`, which a dotted path cannot match. The plan's gate,
   "counting remaining `RawIDFilter()` matches", would pass on a database where nothing was
   converted. `TestRawIDFilterTargetsTheOnlyPersistedID` pins the stale string.
   [plan.md](./plan.md) § What it converts names the same three pre-reshape paths.
7. **The step must follow the reshape, not only the owner stamp.** The worker decodes into
   `models.Job` and writes the struct back. Before the reshape the rows are at
   `build.costs.linkedJobs[]`, which the model no longer declares, so `Encrypt` finds no targets,
   stamps `protected.spec`, and the document is recorded as converted from a struct that never
   held its rows. [archived-jobs-stats/plan.md](../archived-jobs-stats/plan.md)
   § release steps tells an operator to run `tasks encodeJobIdentity` before `prepareRelease`,
   which is that order.
8. **The wire table's last row is stale.** "Browser `upgrade_scopes` — unchanged": nothing in
   `frontend/src` sends it. The name survives only in a log-consolidation list
   (`services/websocket/server/ws_message_operation.go`) and a comment (`server/types.go`).
9. **More than two projects keep this folder alive.** The plan names shared-planners and
    archived-jobs-stats. auth-hardening cites it too (`contents.md`, `plan.md`, `current-state.md`).
10. **A promotion target carries a stale path.** `backend/api/auth/sessions.md` § keys cites
    `services/shared/core/crypto/keyrings/refresh_token.go`; the file is
    `services/shared/crypto/aesgcm/keyrings/refresh_token.go`. It also describes the
    `custom_claims_*` keys as an advisory grants cache, which item 2 contradicts.

## Decisions needed

### 1. How the conversion runs inside the window

**Question.** Does the `prepareRelease` step convert documents itself, or queue the worker tasks
that do?

**Why it is James's call.** The plan says "as a `prepareRelease` step" and stops there. Core, where
`prepareRelease` runs, is not given `ENTITY_ID_KEY` (`docker-stack.yml` `x-secrets-core`) and builds
no cipher, so converting in-process means widening who holds the one secret the design rests on.
Queuing means the gate cannot pass in the run that queued the work.

**Options.**

- **Convert in-process in core.** Mount `ENTITY_ID_KEY` on core, build the cipher in the command,
  convert after the reshape. One run, and the gate at the end is meaningful in that run. Costs a
  fourth holder of the key (core already holds `REFRESH_TOKEN_AES_KEY`), and the work sits inside
  `prepareRelease`'s ten-minute `ctxRun`. The worker task and its NATS definition then have no
  caller and are deleted.
- **Queue from the step, gate on a second run.** The step publishes per-owner tasks; the first run
  ends with the gate failing (it is not `required`, so the run finishes and exits non-zero), the
  operator waits for the queue to drain and runs `prepareRelease` again. No stack change. The
  window's length depends on a queue, and the release's own instructions gain a wait.
- **Keep it a command run before the window**, as `rewriteOwnerScopedIDs` is. Ruled out by
  Discrepancy 7: before the window the documents are neither owner-stamped nor reshaped.

**Recommendation.** Convert in-process. The reshape already does this kind of work in the same
command over the same collections, the gate then proves the run, and it removes a command an
operator has to know about. Take the live document count first to confirm the timeout holds.

**Blocked until decided.** Work items 2–5 of the conversion, and the stack change if chosen.

### 2. What the gate counts

**Question.** Does the gate count documents holding a raw id, or documents not on the current spec?

**Why it is James's call.** The plan says raw ids. After the reshape that filter cannot be written
as a dotted path, and the two definitions fail differently.

**Options.**

- **Stale spec** (`StaleSpecFilter()`). One filter that survives any future move of
  the rows. `Encrypt` stamps the spec only after converting, and the worker refuses to write a
  document on which a raw id survived, so "spec is current" already means converted. It also
  refuses a release in which the worker skipped a document it could not decode, which
  `EncodeJobIdentity` logs and passes over while still reporting success.
- **Raw id present**, rewritten for the keyed shape with `$objectToArray` over
  `esi.industryJobs`. States the actual privacy fact, at the cost of a collection scan and a
  filter that must be rewritten whenever the declaration gains a line type.

**Recommendation.** Stale spec, as the single selector for enumeration and gate, which is how the
`rewriteOwnerScopedIDs` pair is built. Delete `RawIDFilter()` rather than keep a second definition
of "needs converting".

**Blocked until decided.** The gate, the enumeration fix and the owed test.

### 3. Where the plaintext refresh-token rows are removed

**Question.** Is the removal a `prepareRelease` step in the shared-planners window or its own
`tasks` command, and does anything change if the live count is not what dev suggests?

**Why it is James's call.** The plan lists both and marks it "not yet decided". The choice also
decides whether the model change (work item 3) can ship in this release or waits for a later one.

**Options.**

- **A step in this window.** Inside the copy, written down with the rest of the release's data
  work, and it lets the model change ship in the same build. Requires the live count before the
  window so the step is written against what is there.
- **A standalone command.** Can run any time, but nothing forces it to have run before the model
  change deploys, and it sits outside the backup.
- **Encrypt rather than remove**, if the count shows rows on cloud accounts. The plan's reasoning
  for removal assumes they are all on accounts with cloud storage off.

**Recommendation.** A step in this window, removal only, with the count taken first; if the count
shows any row on a cloud account, stop and re-decide, because cloud maintenance should already have
repaired those and their presence would mean something else is wrong.

**Blocked until decided.** Work items 2–4 of the fallback cleanup.

### 4. Who closes the ref leak on organisation-owned deliveries

**Question.** Does this project extend `ClientPayload` to cover `_id`, `docID` and `_meta.owner`
before corporation planners ship, or is it accepted as opaque ciphertext?

**Why it is James's call.** shared-planners recorded it at Stage G and declined to act; this
project's overlay states the rule it breaks; neither plan lists it as work.

**Options.**

- **Fix here, before shared-planners Stage F.** This project owns `ClientPayload` and the rule.
  Strip `_meta.owner` (the handle is already top-level) and rewrite an owner-key `_id` and `docID`
  to the handle. shared-planners § Stage G, G5 says the SPA settings handler keys on `owner`, not `docID`, so by that account it is not
  disturbed.
- **Accept it.** A ref is opaque without the key and nothing in the SPA reads these fields. Then
  the overlay's "refs must not reach a browser" and `routingOnlyFields`' comment are wrong as
  written and should say so.

**Recommendation.** Fix here, and make it a named prerequisite of Stage F in shared-planners'
§ What the other projects owe, which currently says "no change owed".

**Blocked until decided.** Nothing today. It must be settled before any organisation-owned
document is written.

### 5. Whether the raw-id session remains go now

**Question.** Is the dead `custom_claims_*` cache removed in this project now, or left for
shared-planners Stage I?

**Why it is James's call.** The overlay hands it to shared-planners; the code shows it has no
reader, so nothing in Stage I's open question about the grants ceiling depends on it.

**Options.**

- **Remove now**, with the keys either left to expire inside 30 days or dropped by a release step
  beside `dropRetiredMarketKeys`. Makes "Redis holds no entity ids" true at this release.
- **Leave for Stage I.** No work here, and the statement stays false until an open stage closes.

**Recommendation.** Remove now and drop the keys in the window. It is deletion only.

**Blocked until decided.** Nothing; it is independent of every other item here.

### 6. Whether a decode command is owed

**Question.** Is the release copy enough to unwind a conversion, or is `decodeJobIdentity` written?

**Why it is James's call.** [plan.md](./plan.md) § Reverting a conversion lists the missing command
as a gap without saying whether to close it.

**Options.** Rely on `revertRelease` once the conversion is a step inside the copy; or write a
decode sweep that walks the same declaration.

**Recommendation.** Rely on the copy. A ref decrypts for as long as the key exists, and every
read already restores the id, so a decode command would only ever undo storage.

**Blocked until decided.** Nothing; it closes a line in the plan.

removal run. Within it, the conversion follows "reshape every job document"
